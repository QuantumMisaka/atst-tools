ATST-Tools GitHub 治理与发布前门禁设计

状态：本地实施完成，待 GitHub 设置与发布后外部验收

决策来源：2026-09-04 用户确认“硬门禁 + 人工跨模型终审”，并要求 README、用户文档和开发者文档在推送 main 前反映最新稳定态。

实施前基线（2026-09-04）

在 Task1-3 实施前，包单一版本源为 pyproject.toml 的 2.2.3；对应的 release note 和预期 v2.2.3 发布标识必须与该稳定版本一致。本地 main 包含待推送的文档/MPI 改进。基线中的 tests.yml 仅覆盖 PR，publish-pypi.yml 在 v* tag push 或手动 ref 后直接 build/Twine/upload；发布文档却陈述“GitHub Release 触发”、deepmodeling 所有者和 2.1.0 示例。

当前本地状态（2026-09-05）：仓库文件现已定义 tests.yml 的 PR、main push 和手动触发，并由独立文档治理 job 运行文档检查；发布工作流先解析 ref，再由 release-preflight 完成发布前机械门禁，最后才进入带 OIDC 的 PyPI upload job。这些是本地 workflow 定义，不表示 GitHub workflow 已执行，也不表示外部设置已通过。

目标与非目标

  • main 与 PR 均有可重复的测试和文档治理 CI。
  • 任何 PyPI 上传前先对同一 tag/ref 通过发布就绪检查、完整 pytest、文档治理、构建、Twine 和 clean-wheel API 验证。
  • 用户/开发者入口及发布文档从单一稳定版本事实得到一致、可回归的说明。
  • 将跨模型治理终审保留为真实的人工受控门禁，而不是在公共 CI 中伪造模型审查。

非目标：不推送、不打 tag、不发布 PyPI、不配置 GitHub 环境或分支保护、不自动同步 Gitee；这些是维护者授权的外部动作。

架构与决策

  1. 仓库内机械门禁：scripts/check_release_readiness.py 接受 --tag 与可选 --root，读取 pyproject.toml，验证 v-prefix、版本、docs/releases/RELEASE_NOTES_<version>.md 和 Compatibility package-version 行。它不访问网络、不创建 tag、不发布。
  2. 常规 CI：保留现有 tests workflow，增加 main push，并拆出文档治理 job。两者均 contents: read。
  3. 发布 preflight：发布工作流先解析 tag/ref，再在同一 ref checkout 安装 dev 依赖并完成 R5，上传已检查的 distributions artifact；publish job 下载唯一 artifact 并使用 pypi Environment/OIDC 上传。
  4. 人工治理：AGENTS/GOVERNANCE_REVIEW 的跨家族终审由受控 launcher 完成；其结果包是审阅证据，不进入发布工件，也不由 Actions 伪造。GitHub 分支保护和 pypi Environment 审批由仓库管理员在设置页配置。

失败处理

  • tag 不以 v 开头、版本不匹配、release note 缺失或 Compatibility 行不匹配：preflight 失败，upload 不可运行。
  • pytest、文档治理、build、Twine 或 wheel gate 失败：artifact 不上传，PyPI job 因 needs 不会开始。
  • 治理文本有实质改动却没有独立跨家族审查：维护者不得 tag/release；CI 成功不等价于该门禁通过。

实施与发布后检查

  1. 先以 TDD 实现脚本、workflow 契约和文档事实修正；完成本地机械门禁后，治理路径变更仍须按现有流程完成独立跨家族终审。
  2. 经授权 push main 后，确认 GitHub Tests/Governance jobs green；维护者手动从 GitHub 拉取同步 Gitee 后，检查两端 README 指向相同用户指南/示例。
  3. 下一次 v<version> tag 发布前，配置 GitHub main branch protection、pypi Environment review/tag restriction 和 PyPI Trusted Publisher 的 QuantumMisaka/atst-tools 绑定；发布后在干净环境安装并检查 PyPI README 链接。
本地 Markdown/HTML 为规范源；Gitee 继续由维护者手动同步，不产生专属代码或自动化。
